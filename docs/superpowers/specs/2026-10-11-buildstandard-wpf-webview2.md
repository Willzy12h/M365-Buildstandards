## 1. Decision summary

**Build a coherent native Windows workspace with the recovered Astra concept B command centre and concept A working context. Use WebView2 only for the first catalogue-reference reader. Generalise the product to BuildStandard.**

This is a specification of intended behaviour, not a statement that it is implemented or tested. The earlier proposed design and consolidated review remain evidence inputs. This document supersedes their conflicting visual assumptions and their fixed Claude/App versus Astra/engine ownership arrangement for the next authorised phase.

| Topic | Consolidated design decision |
|---|---|
| Working application | .NET 10, WPF and the existing shared execution/evidence engine. Native forms, grids, navigation, identity, approvals, results and recovery. |
| Visual reference | The supplied `hybrid-b-context.html` concept and its Home, Report and Companion images: teal accents, pale workspace, white cards, horizontal primary navigation and persistent working context. Not the frozen application's permanent navy sidebar. |
| First reader | One catalogue-only Engineer Build Standard document, generated by the existing renderer and opened at the selected control anchor. No tenant-report hosting in this slice. |
| Reader containment | One local mapped document, no scripts, host objects, web messages, generic browser or native-command bridge. Native toolbar, identity and actions. |
| Availability | Managed Evergreen Runtime, initialised only for the reader. Native work and the offline CLI remain usable when preview is unavailable. No silent installation or policy bypass. |
| Pinned context | An optional **docked native details panel** in the first design. An independently detached companion window remains a later scope, not implied by the concept screenshot. |
| Neutral identity | BuildStandard; subtitle “Engineer workspace”. Remove organisation-specific branding and non-essential remarks from active product surfaces, defaults, maintained source commentary and current documentation. Preserve legitimate historical evidence and required notices. |
| Initial responsibility | ChatGPT leads the initial work across components. Claude participates later only when William requests a bounded contribution or handoff. Independent safety review remains necessary; implementation approval has not been given. |

The intended outcome is that an engineer unfamiliar with the implementation can identify the client and evidence, understand what is known, select the next appropriate task, review a proposed change and interpret its result without reconstructing state across screens. A reference document must never acquire authority merely because it is displayed inside the application.

| Proposal or disagreement | Disposition and governing requirement |

| Copy the concept HTML into the application shell | **Rejected.** Translate the visual intent into WPF. The first WebView2 surface is the document reader only. |
| Build both a control reference and manual-guide reader immediately | **Narrowed.** First embed `EngineerDocumentKind.BuildStandard`, opened at a selected control. Existing manual-guide export remains available; embedding it is a later extension using the same host, not another renderer. [C §5.1; G §4] |

| Fall back from virtual-host `Deny` to `DenyCors` if fragments misbehave | **Rejected.** Those values govern cross-origin resource access; `DenyCors` is less restrictive. Fragment behaviour is not a reason to relax the boundary. [V2, V3] |
| Handle every fragment through `NavigationStarting` | **Corrected.** Same-document fragment changes do not fire that event. Use source/history observations for location display and maintain document identity separately. [V3] |
| “Showing CA-001” always describes the current scroll position | **Rejected.** An anchor is not continuous reading-position tracking. Use “Opened at CA-001”, or an accurately observed anchor label; never infer the current section from a stale initial anchor. |
| Put approved deviations within a “Meets” count | **Rejected.** Approved departures and non-applicability remain separately labelled. They are not machine-confirmed compliance. Partial matches and missing recipe matches also need their original qualification. [S3; R §4] |

| Every written CA row is labelled “disabled” | **Rejected unless supported by the row's evidence.** Intended disabled state and observed readback are different. Unknown acceptance/readback cannot become a confirmed disabled object. |
| Force focus into the document when an asynchronous load finishes | **Narrowed.** Move focus only if the user remains in that reader and has not moved it elsewhere. Late completion must not steal focus. |
| Restore old page state after a client/standard switch | **Rejected.** Back restores state only within the original still-valid context. Supersession returns to the current context and discards old selections, links and callbacks. |
| Apply one global grid Tab rule or move all dates to DatePicker | **Narrowed.** Required keyboard tasks govern; editing and checkbox semantics cannot regress. Date-control changes outside selected screens are not brought into scope. |
| Separate permanent agent ownership blocks GPT desktop work | **Superseded by William's latest instruction.** ChatGPT is the initial lead; no existing Claude branch is overwritten and no safety review is waived. |
| Remove all old organisation strings indiscriminately | **Rejected as a migration method.** Generalise active product identity comprehensively, but preserve original evidence, required notices and exact compatibility/provenance references. D-07 defines the boundary. |

These dispositions do not reopen withdrawn CLA-R-003/012/026 allegations as new engine defects. CLA-R-013's reported keyboard burden is stronger in Claude's follow-up, but no arbitrary stop quota is adopted. No current product defect is inferred solely from a concept or seeded screenshot.

## 5. D-05 — native visual and interaction specification

### 5.1 Visual language

Use the recovered concept's **teal, pale-neutral and white** composition, with dark readable typography, lightly bordered cards, restrained filled actions and a highlighted next-task panel. Retain standard Windows window controls and native input/automation behaviour. No browser frame, duplicate HTML shell or screenshot-as-XAML reproduction.

Starting normal-theme tokens from the original HTML are `#152C38` text, `#627580` secondary text, `#007B79` teal, `#F2F5F5` workspace and `#DCE5E8` borders. These identify the design reference, not approved accessibility ratios. Contrast, selected/focused states and Windows contrast themes take precedence over matching a hex value. Do not copy the concept's small fonts, fixed heights or disabled-button contrast uncritically. [A1]

Use one semantic set of shared WPF resources and a small corresponding stylesheet for generated documents. This does not require a new token-generation framework or third-party control suite. Changes to shared document styling affect future preview and export identically; historical saved HTML remains unchanged.

Remove the concept-only switching bar (“Command centre / Report detail / Pinned details”), illustrative control disclaimers and company strapline from the normal product. Keep conspicuous synthetic/demo labels when demo data is actually shown. Demo identities, counts and progress must never appear in an ordinary empty workspace.

### 5.2 Shell and navigation

The native shell contains a compact product/account row, a client/access row, an evidence-context strip, primary navigation and the task area. Keep the currently acting tenant and actual resource/account authoritative. In offline mode say **“No live connection — saved evidence”**; do not present a remembered account or avatar as signed in. A privileged setup session identifies its own actual tenant and account, even if a different client is selected elsewhere.

Primary native navigation follows the concept: **Workspace, Build standard, Reports, Scripts, Settings**. Preserve existing route identities and services; regroup their entry points rather than create duplicates.

| Primary group | Existing responsibilities reached through it |
|---|---|
| Workspace | Command centre, client connection and setup, overview/licences, jobs, saved evidence/drift, history and recovery |
| Build standard | Catalogue/reference, Configuration, Assessment, Deviations, Plan, Deploy, manual checks and separately guarded Policy automation |
| Reports | Existing Graph reports, registered Exchange reports, mailbox-capacity review and naming/report views |
| Scripts | Existing Copy/Save library and its supported boundaries; no “run anything” interpretation |
| Settings | Configuration, existing prerequisite checks, diagnostics, evidence transfer and support functions |

Contextual subnavigation exposes the current workflow without a permanently tall 21-item global rail. Friendly labels lead; exact source route keys remain internal. Route references and any step numbers derive from the same metadata. Current task and route remain visible when navigation wraps or moves into an accessible menu. Secondary shortcuts may open an existing page but do not constitute another implementation.

### 5.3 Command centre

Use the concept's four principal task cards: **Discover the tenant; Assess saved evidence; Backfill an existing build; Review a change plan**. Each opens an existing guarded workflow. Discovery is clearly identified as a potential tenant-read operation and never runs merely because a card or page is displayed. A route that is unavailable explains why; it must not pretend an illustrative feature exists.

Below the task entry points, use **Recent evidence** and **Needs attention**. Recent records show friendly name, original source/capture time and honest state; open actions use the record's own identity. Needs attention consumes the shared D-04 projection, not another decision engine. The selected primary recommendation has a clear reason and route. Supporting records may appear only where the existing local projection can substantiate them; do not invent a new aggregation service or run broad I/O on every header refresh.

Display progress only for actual tracked work. “5 of 8 sections processed” is task progress, not completeness or compliance. If a denominator is unknown, use an indeterminate state and completed-work description rather than a made-up percentage. Existing prerequisite results may be reused with their observation time; displaying Home must not trigger the doctor, sign-in or collection.

### 5.4 Working context and pinned details

The context strip shows the working client/domain, connection/mode, selected evidence source, original capture time, scope and coverage/assessment limitations. A catalogue reader instead identifies **“Catalogue reference — not observed tenant evidence”** and its release/digest; the working client and document source remain different facts.

Provide an optional **native docked details panel** for exact identifiers and source provenance. Unpinned details follow the current selection. Pinning deliberately captures an immutable reference to an existing saved record, not a copy of authentication or approval state.

A pinned reference may remain while navigating. If the main workspace changes client, retain the pin identity but show a persistent **“Pinned reference is for a different client”** banner within that self-labelled panel; sensitive detail is collapsed until explicitly reopened. Never silently repin it or mix its rows/counts into the new client's current result. Copy from the panel, when deliberately used, copies the pinned record's own clearly labelled information. It cannot approve, run, export through the new client's toolbar or change the authenticated client. Repin and close are explicit native actions.

On narrow/short screens use a docked drawer or stacked panel; opening details must not obscure an approval, essential warning or focused input. A detached companion is **deferred**. Its screenshot establishes visual intent only, not approval for a new multi-window subsystem.

### 5.5 Assessment and report-detail layouts

Keep the concept's focused next step and nearby working-context summary, implemented with native controls. Report source tables and interactive findings stay WPF; the report-detail concept is not permission to embed tenant reports.

Assessment uses a prioritised native finding list and nearby detail. Wide screens place them side by side; narrow screens stack or reveal the detail without losing the selected record. Introductory prose, exports and full counts must not consume the entire initial task area. The initial populated view should show usable findings and a clear path to detail; a row-count quota is not a substitute for task acceptance.

Use compact native filter summaries without changing engine statuses:

| Summary | Underlying state and qualification |
|---|---|
| Matches the standard | `Compliant` only, scoped to the evidence and assessment |
| Needs review | `Missing`, `PartialMatch`, `RequiresManualReview`, `LicenceUnavailable`, with separate subcounts and original row labels |
| Enforcement needs review | `SettingsMatchNotEnforced`; distinguish observed disabled/report-only/unassigned from enforcement that could not be established |
| Could not assess | `UnableToAssess`; not a pass, failure of the requirement or absence of objects |
| Separate labelled counts | `CompliantWithDeviation` as “Approved deviation”; `NotApplicable` as “Not applicable” |

Every finding belongs once to its presentation group; the original status remains visible. “No recipe match” does not assert that no equivalent protection exists. Collection completeness and not-attempted source states remain a separate dimension. No compliance percentage is inferred from available sources. [S3; R §§4–5]

Keep a selection by stable identity only while its tenant, catalogue and source context remain valid. A filter may hide it with an explicit indication, but a rerun or source change must clear/rebind old detail to the new validated result; preserving an ID is not permission to preserve stale content.

### 5.6 Plan, Deploy and results

Plan distinguishes current selection from **Last built plan**, its source and validity. Before obtaining different access, explain that the prior capture/assessment/plan and approval will be invalidated. Retain necessary native confirmations. Reuse visual frames where useful without merging consent, tenant-write, Copy/Save and recovery authority contracts.

Place decision-relevant columns before supporting metadata. Keep exact values in accessible, selectable detail; do not make tooltips the only way to read them. A disabled action gives a visible reason from the current state, not an assumed diagnosis. An object name cannot substitute for a verified ID or silently trigger new permissions.

Use a shared native outcome component with independent dimensions: task lifecycle, read completeness, request acceptance, configuration readback, saving/integrity and effective protection. Only show dimensions that apply.

- **Failed empty read:** “Could not check — this read failed. Zero returned rows do not establish that no objects exist.”
- **Successful empty read:** “Checked successfully — no objects returned within this report's scope.”
- **Partial read:** “Partial read — some results are unavailable”, retaining available rows and limitations.
- **Known disabled candidate:** “This candidate is disabled; it does not enforce the control. This result does not establish overall tenant protection.”
- **Intended disabled state, unknown readback:** “Requested state: disabled. Current state not confirmed.”
- **Saved output:** “Saved — integrity checked” only when the application actually performed the corresponding integrity check; otherwise simply “Saved”.

Do not forbid the word “Completed” in every context: a finished process can have partial data. Do not report “nothing was sent” for an entire run when earlier rows were sent. CLA-R-008's manual-attestation semantics remain unresolved; this design neither relabels all manual Pass records as machine proof nor changes their persisted contract.

### 5.7 Keyboard, focus and display envelope

Use native WPF input, selection and validation. Provide an accessible skip-to-content route, page-search shortcut where applicable, and task-appropriate grid navigation. Do not globally force a single Tab behaviour until checkbox and editable-cell operations work. Enter must not accidentally submit a tenant write; existing deliberate approval semantics remain.

Use real heading and status-announcement semantics. Errors require timely, meaningful announcement; progress should not repeatedly interrupt reading. Setting an automation property alone is not proof that Narrator receives the correct event. Asynchronous refresh must not move focus after the user has moved on.

Preserve the earlier logical render sizes for regression continuity, not as a minimum-window requirement. The proposed target includes the available Windows work area on a 1920×1080 display at 100%, 125%, 150%, 175% and 200% scaling. This is a target to validate, not a current support claim. Compact the context strip, group navigation and stack details before requiring horizontal whole-window scrolling. System taskbar/title-bar space must be accounted for. Full evidence paths and hashes remain accessible in details rather than permanently crowding the working area.

## 6. D-01 to D-04 — shared technical and safety contracts

### D-01: access truth

One reviewed capability meaning feeds connection admission, native header/detail and current packaged guidance. Distinguish toolkit mode, observed token capabilities, actual verified resource/account/tenant and individual operation opt-ins. Classification must not rely on the two existing spelling substrings. Handle known read capabilities, explicit protocol scopes, supported resource-qualified forms, broader permissions and unclassified outcomes conservatively. [G §3.1; R GPT-R-001/012]

A dedicated assessment registration cannot be represented as verified read-only when its returned capabilities are broader or unclassified. Retain the documented shared-registration exception, visibly qualified; do not incidentally remove it or widen its authority. An unknown resource/scope never becomes harmless because its spelling lacks “Write”. Graph assessment mutation guards remain independently authoritative.

Use **“Assessment mode — toolkit changes blocked”** separately from **“Token: read-only capabilities verified / broader permissions present / not fully classified”**. Token capability is not proof of role sufficiency or successful API access. Show “No live connection” rather than a token claim offline. Tenant-change opt-in and registered Exchange Run opt-in use their own labels. No opt-in grants consent, no sign-in makes all reads successful, and neither field is an authorisation engine.

### D-02: freshness and the initial dispatch boundary

Retain configured age limits, original approval identities and existing equality/expiry semantics. Revalidate after awaited preflight and before admitting the current write. A successful slow preflight must not extend the reviewed inputs' lifetime. [G §3.2; R GPT-R-002]

The intended boundary is the **last cancellable admission before the initial request is handed to transport**. If token acquisition or queuing intervenes, preserve the immutable validity requirement across that wait; do not quietly refresh the plan or claim zero-time atomicity with the remote service. Method signatures and scheduling are planning details, not supplied here.

Before that boundary, an expired row remains not attempted, with a durable reason. After transmission may have occurred, preserve accepted/rejected/uncertain semantics, earlier rows and no-uncertain-replay behaviour. Cancellation is not evidence that a request never reached the service. Existing storage, identity, ownership and payload safeguards remain in force.

### D-03: current-context admission

Every current result, selection, copy/export action, delayed completion and notification binds to appropriate tenant/profile/catalogue/evidence and connection-generation facts. A same-tenant account or connection replacement matters; a tenant-string comparison or editor-only digest is insufficient. Reuse the existing stronger report admission pattern rather than claim all paths already have it. [G §§2, 3.3]

On context change, immediately invalidate current transient presentation and commands; preserve original durable history. Late work may be preserved under its original provenance but may not appear as the new client's result. The separately labelled pinned reference is not a current-result exception: it has no authority and no access to the new client's action toolbar.

For D-06, catalogue data does not become client data. Nevertheless, close the reader on working-client, account/connection, standard or selected-document replacement to keep return state unambiguous. Do not restore old client state after that close.

### D-04: one presentation decision

Use a small pure projection of validated current facts for the next-action recommendation, reason, route, priority and disabled explanation. Reuse `HomeTaskProjection`'s approach and remove competing decision trees, rather than add a third projection beside them. The header and Home may use shorter/longer presentations of the same meaning. [G §3.4]

Precedence is: active operation/its stop state; current-client uncertain or interrupted write/history; missing valid client/standard; active privileged setup; a relevant recorded run awaiting outcome review; evidence availability/freshness/completeness; assessment; selected plan/access requirements; exact approval readiness. Current-run review precedes the null-snapshot branch. Historical reviewed records must not trap the user in an obsolete next step forever.

This is navigation guidance, not execution permission. Guarded services revalidate when called. No deferred UI optimisation may delay authority invalidation. A shared presentation projection is not a database, notification-framework rewrite or a claim that the performance hypothesis GPT-R-008 is measured.

## 7. D-06 — contained catalogue reader

### 7.1 Content and entry

First scope is **The Build Standard**, `EngineerDocumentKind.BuildStandard`, using `EngineerStandardDocuments.Html` and verified catalogue input. It generates the whole catalogue and opens at the selected control's existing anchor. There is no new per-control renderer. The source is static HTML/CSS with encoded text and no required scripts; this is source inspection, not hosted-runtime acceptance. [S1; G §4]

Entry is one native **View reference** action in the selected control's Build standard detail. The native toolbar supplies Back to control, source/release, document identity, Save HTML and an explicit external-reference action. Manual-guide embedding, full defaults-document embedding, Assessment-entry shortcuts, tenant reports, diff viewers and print/PDF features are deferred. Their existing exports remain where already available.

The reader replaces only the task-area content. Current client identity and catalogue-document identity are labelled separately. It does not sign in, collect, open a job, change a tenant, approve a plan or make reference PowerShell executable.

### 7.2 Preview/export identity

Generate one admitted document version from one catalogue snapshot, renderer/presentation version and document kind. Record its actual UTF-8 byte digest separately from catalogue digest and generation time. The current exporter writes UTF-8 without a byte-order mark; preview/export must agree on the same encoding and content. [S2]

Save HTML uses those same bytes or an independently checked identical regeneration against the immutable descriptor. Reuse existing export/persistence infrastructure; do not regenerate from a mutable current catalogue while claiming it is the displayed version. A mismatch is an export-consistency failure, not a successful matched save with a quiet warning.

Changing branding, CSS or a content-security policy creates new document bytes and a new generated-document identity, even if the underlying catalogue is unchanged. Historical HTML is not rewritten. A future PDF or sanitised derivative must identify itself as a derivative, never borrow the original HTML/evidence hash.

### 7.3 Local origin and restrictions

Use one app-owned content directory containing the admitted document only, mapped to **`https://reader.buildstandard.example/`**, with the document path and selected fragment explicitly admitted. The directory is separate from the browser profile. Do not map the entire viewer root, `data`, reports, repository or user profile. No localhost server or CDN is introduced.

Use `CoreWebView2HostResourceAccessKind.Deny`. Microsoft defines this as denying cross-origin resource access; `DenyCors` allows some cross-origin subresources. Neither value alone is an outbound-network firewall. Same-document fragments are not cross-origin access and do not fire `NavigationStarting`. [V1–V3]

Default-deny document policy is required: only the admitted document and legitimate same-document anchors; no arbitrary path, query, redirect, frame, new window, downloadable resource or URI scheme. Use appropriate native navigation/resource/permission controls and restrictive document CSP with no script/connect/frame/object/form/base capability. Permit only the required inline or approved local styles; use system fonts. No broad web-security-disabling arguments are allowed. The precise enforcement is subject to negative hosted tests, not assumed from a handler's existence.

Explicitly disable page scripts, script dialogs, web messages, host objects, autofill/password persistence, DevTools and default browser menus. Never inject code with `ExecuteScript`, document-created scripts or CDP as a substitute: disabling page scripts does not disable host-injected script execution. Preserve needed keyboard selection/copy, find and zoom through supported non-script facilities. No native-command bridge is added. [V4, V5]

Initial setup must apply required restrictions before admitting document navigation. If the installed API/Runtime cannot apply a required restriction, fail the reader closed and retain the permitted native export route. Do not silently weaken the policy to make a document render.

The document-origin requirement is **no external resource fetch or tenant operation**. Runtime servicing/diagnostic traffic is a separate platform/organisation policy matter; this design does not claim the entire process makes zero network connections.

### 7.4 External references and fragments

An external document link remains blocked inside the reader. A deliberate user-initiated reference selection from the current admitted document can populate a native pending-link field. The default approved external destination is exact HTTPS host **`learn.microsoft.com`**, standard HTTPS port, no embedded user information and no misleading suffix/prefix host match. Show the destination before a native **Open Microsoft reference** action. Other hosts remain non-launchable references until explicitly reviewed; no wildcard “Microsoft” substring rule.

`SafeLink` is useful for HTML generation but checks scheme only; it is not reused as the complete launch policy. Validate the pending link again against current document identity at the moment of launch, and clear it on supersession. The external browser's subsequent policy/redirect handling is outside the embedded reader; no claim is made to control it. [S1; G §4]

Internal area/control anchors remain normal links. Observe source/history changes for accurate anchor state, not only `NavigationStarting`. Use “Opened at <control>” unless the current anchor has actually been observed. Do not claim the user's scroll position. An invalid/missing control anchor produces a truthful native notice and access to the catalogue index, not a success claim for the missing section. [V3]

### 7.5 Runtime, content/profile storage and lifetime

Default is an **organisation-managed Evergreen Runtime**, detected lazily at View reference. The WebView2 SDK/loader would be a declared application dependency; the production Runtime is a separate prerequisite. No bundled Fixed Version, silent bootstrapper, elevation or policy bypass is included. Ordinary WPF startup and offline CLI behaviour must not depend on opening or initialising the reader. [V6]

Use **`%LOCALAPPDATA%\BuildStandard\Reader\<application-instance-id>\<viewer-session-id>\`**, with separate app-owned `content` and `profile` children. These are transient local presentation data, not authoritative evidence. They are excluded from evidence/transfer/adoption/support/catalogue bundles, regardless of what the browser writes into them. Do not redirect them into an existing portable evidence root or reuse a normal Edge profile. The exporter remains free to save an explicit user-requested HTML copy to its normal approved destination. [G §2; C F2]

One active reader per application instance is sufficient. Leaving it disposes its owned controller/environment as appropriate and retires that session. Cleanup waits for the relevant browser-profile/process lifetime, not just control disposal. Shared or concurrent processes must not be killed. A narrowly scoped instance/session lease and app-owned marker prevent deleting another active viewer's cache; paths/reparse points require validation before deletion.

Cleanup failures are recorded as **“Reader cache cleanup incomplete”** without claiming secure erasure. A later sweep touches only confirmed retired app-owned sessions. A failed load, crash or standard-user permission denial must not lead to unsafe broad deletion. User-data folders require writable storage and do not disappear automatically for ordinary WPF hosting. [V7]

### 7.6 Reader states and return behaviour

| State | Required native behaviour |
|---|---|
| Closed | No active reader or stale browser callbacks; normal task controls remain. |
| Preparing / loading | Native title/source and Back available; show actual stage. Do not display old content while preparing a new document. |
| Ready | Expected document identity, current generation and successful navigation confirmed. Say “Document displayed”, not “evidence verified”. Preserve user focus unless a still-current explicit transition requires it. |
| Runtime unavailable / blocked | Distinguish an absent detected Runtime from a safely known initialisation error; do not diagnose every failure as “not installed”. Offer a valid permitted HTML export without bypassing policy. |
| Cache unavailable | Explain the safely known local-storage problem. Export only if its separate destination is usable. |
| Document invalid / generation failed | No stale document. Export of that invalid generation is unavailable; retain native catalogue inspection and the exact limitation. |
| Render/process failed | Hide failed content, retain native context and offer deliberate Retry/Back/export of an already valid document. Retry never reconnects or recollects. |
| Superseded | Immediately hide content, clear pending links, cancel/discard late presentation and retire the viewer. Return to the current valid native context, not the former client/release. |

Within the original unchanged context, Back restores release, filters, selected control, scroll position and appropriate focus. After a context change, only currently valid state may be restored. A late navigation/export event must not steal focus or announce itself under a new client.

Use a bounded, non-overlapped web rectangle with native actions outside it. Loading/error states replace or hide that rectangle rather than depend on WPF overlays. Microsoft documents airspace differences between standard WPF hosting and the composition control; no variant is declared accessible merely because it resolves z-order. The standard control is the default to evaluate for this non-overlapping layout; change it only against the same keyboard, assistive-technology and rendering criteria. [V8]
