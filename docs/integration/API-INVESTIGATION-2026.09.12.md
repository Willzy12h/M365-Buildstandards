## Reading the matrix

R/W means delegated read/write permissions. **Existing** means already requested by the .11 assessment/deployment applications, not already consented in any particular tenant. **New** scopes require updated application configuration and administrator consent to both applications again. Read scopes never authorise writes. Tenant roles and licence assignment must also be checked by the engineer.

Intune device configuration routes use `DeviceManagementConfiguration.Read.All` / `DeviceManagementConfiguration.ReadWrite.All` (existing). App routes use `DeviceManagementApps.Read.All` / `DeviceManagementApps.ReadWrite.All` (existing). Enrolment routes use `DeviceManagementServiceConfig.Read.All` / `DeviceManagementServiceConfig.ReadWrite.All` (existing). All require an active Intune entitlement and supported target devices. Settings Catalogue reads/creates are `/beta/deviceManagement/configurationPolicies`, with `/settings` and `/assignments` reads; native definitions are `/beta/deviceManagement/configurationSettings`. Exact definition IDs not confirmed from a Microsoft catalogue reference must not be invented. Client-supplied catalogue instances retain the existing live-definition validation before any candidate write.

Native Windows CSPs below use the existing documented `windows10CustomConfiguration`/OMA-setting transport where already supported; they are built-in OS policies, not uploaded ADMX, imported custom policy templates, platform scripts or remediations. No new script deployment mechanism is introduced. A custom template or script needed beyond those native policies remains a manual proposal. [Graph create route](https://learn.microsoft.com/en-us/graph/api/intune-deviceconfig-windows10customconfiguration-create?view=graph-rest-1.0), [Settings Catalogue](https://learn.microsoft.com/en-us/intune/device-configuration/settings-catalog/common-tasks).

## Decisions and unresolved facts carried into implementation

- Use schema 5 optional, null-omitted metadata for product area, repeatable location instances, stricter public-IP requirements, and the complete manual document sections; retain schema 3/4 loading and historical digest compatibility. Record each concrete field in INT-031 before implementing it.
- Mandatory inputs are conditional on the selected operation/control. A global empty unrelated package field must not prevent saving useful client data. An operation requiring reviewers, a mail domain, location name/ranges or store identity must refuse empty/invalid data clearly.
- Native catalogue IDs not established from public Microsoft sources remain explicitly unverified/manual; never fill them from memory. Device preparation policy, Chrome SSO, OneDrive FOD details, starting taskbar XML, regional setup, file extensions and fast-startup enforcement need the manual paths above where no complete native recipe is confirmed. The ESR successor uses the documented native Windows backup CSP; its device effect remains unverified.
- Implementation boundary: migrated passkey profiles are captured separately and make the legacy reviewed method action refuse. Profile editing and effective Authenticator coverage remain manual. Consent reviewers in this release are explicitly resolved enabled users; group reviewers are not implemented. Managed Google Play capture uses `$select=id,bindStatus,lastAppSyncDateTime,lastAppSyncStatus`; it never requests company enrolment codes. [Documented connection model](https://learn.microsoft.com/en-us/graph/api/resources/intune-androidforwork-androidmanagedstoreaccountenterprisesettings?view=graph-rest-beta).
- Preserve all new candidate invariants and selective, durable reviewed writes. New singleton identity settings and group ownership need independently tested write boundaries; no ordinary candidate POST to a policy singleton.
- Final recommendations: retire classic ENR-003/004 automation from the default device-preparation path; retire SEC-WIN-002 under ESET while retaining SmartScreen unless the maintainer decides otherwise; defer Outlook automatic account configuration; keep script/custom-template deployment out of scope; resolve module retry semantics and the SPF/From trust boundary before future automatic Exchange writes.

Phase 6 source audit: every .12 control now carries a primary Microsoft URL in `references` or `documentationNotes`, including retained controls whose older catalogue had only a source name. Manual identity references use the documented state-only authentication-method PATCH, preserving omitted targeting/features; TAP retains its captured include/exclude targets and refuses incomplete lifetime data. Automatic MDM scope changes first confirm the exact valid Intune discovery policy and warn that `All` replaces selected-group targeting. The beta enrolment model's `androidForWorkRestriction` is confirmed in [Microsoft's Graph documentation source](https://github.com/microsoftgraph/microsoft-graph-docs-contrib/blob/main/api-reference/beta/resources/intune-onboarding-deviceenrollmentplatformrestrictionsconfiguration.md); portal platform tabs need not create the same object grouping. These are documentation checks, not live acceptance.
