## Reuse and supported actions

Reuse the existing broker/cache/verified connection, assessment/deployment separation, tenant write lease, durable evidence writer, payload digest, final-admission guard, single-use approval, unresolved-write blocking, jobs/observations and recovery semantics. Extend the shared engine with an explicit lifecycle action registry/service and versioned evidence types, not a WPF executor, generic JSON/PowerShell runner or second authentication platform. The offline CLI may inspect/export proposals and results, not sign in or execute live lifecycle actions.

The first native journey selects an **existing cloud-managed member user** and exactly one of these fixed action kinds. Workflow checklists can link several separately approved actions; there is no automatic multi-action batch, unattended continuation or rollback.

| Action | Exact v1.0 route/method and body | Approved write purpose | Required observed effect |
|---|---|---|---|
| Add direct member | POST `/groups/{groupId}/members/$ref`; one exact `@odata.id` under `https://graph.microsoft.com/v1.0/directoryObjects/{userId}` | GroupMember.ReadWrite.All | Same group's complete direct membership contains exact user once |
| Remove direct member | DELETE `/groups/{groupId}/members/{userId}/$ref`, no body; `$ref` mandatory | GroupMember.ReadWrite.All | Complete direct membership no longer contains that exact user; no deletion of the user object |
| Add/update direct licence | POST `/users/{userId}/assignLicense`; one selected skuId with exact disabledPlans, empty removeLicenses | LicenseAssignment.ReadWrite.All | Exact direct SKU/disabled-plan state and assignment status read back; unchanged unrelated assignments |
| Remove direct licence | Same action; empty addLicenses and one selected skuId in removeLicenses | LicenseAssignment.ReadWrite.All | Direct assignment removed; inherited entitlements separately observed, never claimed removed |
| Enable/disable account | PATCH `/users/{userId}` with only `accountEnabled` boolean | User.EnableDisableAccount.All plus existing User.Read.All | Same user's accountEnabled equals the reviewed value |
| Revoke sign-in sessions | POST `/users/{userId}/revokeSignInSessions`, no arbitrary body | User.RevokeSessions.All | Accepted boolean plus observed advancement of signInSessionsValidFromDateTime; not a guarantee every application session ended immediately |

Existing unrelated fields, group owners and licensing assignments are not rewritten. No group creation, deletion, dynamic-rule edit, role assignment, password/account creation, licence purchase, mailbox conversion/access, retention/hold change, device action, guest invitation, CA activation or Intune assignment. Exchange actions stay manual. User/group/SKU IDs must be canonical validated GUIDs selected with friendly names; names never establish identity or policy ownership. Existing groups are deliberately authorised lifecycle targets, not silently added to toolkit policy-ownership mappings.

## Read surface and access admission

Preview uses registered GET projections only: selected user identity/accountEnabled/userType/onPremisesSyncEnabled/usageLocation/assignedLicenses/licenseAssignmentStates/signInSessionsValidFromDateTime; selected group identity/groupTypes/securityEnabled/mailEnabled/onPremisesSyncEnabled/isAssignableToRole/assignedLicenses; exact selected group's direct members; subscribedSkus/service plans and selected user's licenceDetails; current directory role assignments and directory role eligibility instances for the target; and the role-assignable group inventory described below. Existing bounded group/user lookup may select exact objects but is not before-evidence.

Reuse existing User.Read.All, Group.Read.All, Organization.Read.All and RoleManagement.Read.Directory where actually returned and documented for the selected endpoint; no Directory.Read.All fallback. All required permissions are previewed for the **selected action**, never silently bundled for unrelated actions. Deliberate deployment mode/access switching reuses the current application setup/session architecture and invalidates previous approvals. Missing returned scope, tenant/account mismatch, unavailable required RBAC or a failed read blocks the action; Graph may require a corresponding administrator role in addition to delegated scopes. Microsoft authorisation, licensing and propagation remain live-unverified until separately tested.

Every required response is strict, bounded, non-null and complete. Preserve per-read status/provenance; permission denial, unsupported/licence-limited API, malformed/duplicate identity, continuation outside the fixed resource, cancellation, timeout or cap means **unable to establish readiness**, never empty-safe. Cap the entire preview at5minutes,100actual requests,5000returned rows and16MiB, counting preflight rereads under their own bounded attempt. The same source scopes/identity must remain valid through await boundaries. Existing same-identity single silent401 read renewal is retained; no interactive mid-operation renewal or write retry.

## Target authority and privilege refusal

Refuse the connected operator's own user, configured emergency/protected identities, guests, deleted/unidentified users, currently synchronised identities and unknown source authority. Returned false on a user may establish no current synchronisation under Microsoft's documented semantics; a missing field does not. Group actions additionally refuse synchronised/previously synchronised groups, dynamic groups, role-assignable groups, distribution groups and unknown unsupported populations. Group membership is direct only; never claim transitive/effective-access coverage or edit a group whose authority cannot be established.

Current and eligible **Entra directory roles** on the target block every lifecycle action. Complete current role assignment and eligibility reads are required; no PIM absence inference from current membership alone. Microsoft's PIM-for-Groups eligibility API needs PrivilegedEligibilitySchedule.Read.AzureADGroup, which is not approved. Do not add that scope. The conservative first implementation therefore also refuses execution if any role-assignable group exists in the tenant, or that inventory is incomplete: it cannot exclude eligible privileged group membership. Only a complete fixed `/groups` filter for `isAssignableToRole eq true`, with all returned identities/type values validated and all pages admitted, may establish the zero-role-group prerequisite. This restriction is visible in readiness, not a hidden error or a claim that the selected user is privileged. If directory eligibility cannot be queried on a Business Premium/P1 tenant, readiness is blocked; a licence label alone never proves no eligibility exists.

These checks concern Entra directory privilege, not proof of absence of all Azure, Exchange, application or external-system privileges. The explicit target review also requires the engineer to confirm the organisation's protected-account list and downstream ownership before approval. Known workload-privileged/protected targets stay blocked; unknown externally managed authority stays manual. No broad global “non-privileged account” badge is derived from these reads. Supporting additional privileged/unknown populations requires a new reviewed contract, not an override checkbox.

## Exact before-evidence, approval and send

Use an independently versioned `lifecycle-plan`/`lifecycle-run` family bound to tenant, operator, client registration/mode, action kind, exact target(s), baseline standard/profile digests, original observation digests, complete action-specific before-values, proposed canonical body/path and consequences. The existing complete deployment snapshot requirement is not weakened or satisfied by a scoped report. Capture fresh complete action-specific before-evidence in addition to that verified snapshot. Reports/imports cannot become write authority.

Previewed evidence remains immutable. Approval is exact, local, explicit and single-use, with the existing original-expiry/time limit; it cannot be refreshed by token renewal. Any changed target/body/access/context/standard/before-value invalidates approval. Before send, re-read required targets/authority/licence/membership state and compare the action-relevant fingerprint. Check the final exact approval and source identity directly before the single send, without intervening await. Microsoft Graph does not provide a transaction across these reads and action endpoints: show this race limitation, preserve server rejection and readback uncertainty, and do not promise atomic tenant locking.

Persist intent durably under the existing tenant write lease before a request may leave. Existing unresolved deployment, reviewed-change, recovery and lifecycle records mutually block further writes; no new family bypasses old blockers. Only registry-generated method/path/body is admitted by the Graph write boundary. Mark “not sent” only when the boundary establishes that fact. Once send may have occurred, Stop does not abort/retry/replay it; wait for bounded response, persist acceptance/uncertainty and perform registered readback when possible. Timeouts, disconnects, malformed replies and5xx remain potentially applied, not automatic failure/retry. Crash after intent but before durable known-not-sent evidence remains unresolved.

Licence actions require complete selected SKU/service-plan/usage-location/assignment-state evidence. Unknown capacity, disabled/suspended SKU or incompatible plans blocks addition; never buy or infer capacity from a friendly licence name. Group-based licensing is explicitly separate; removal cannot remove inherited entitlement. A removal preview, an update that newly disables any existing service plan, and removal from a group with assigned licences each require the exact preservation/retention/business-owner checklist acknowledgement bound to that plan, with consequences and manual Exchange dependencies. The action label does not bypass this gate: `addLicenses.disabledPlans` can withdraw an existing service. Before group membership changes, show the exact returned group licence assignments and potential target effects; missing/unknown group licensing blocks membership execution rather than concealing an entitlement change. Group-based effects remain subject to propagation and separate readback, not guaranteed by membership success. This is a human review record, not fabricated verification of retention/holds. Without it every such service-withdrawing action stays unavailable. Unknown or conflicting assignment errors remain blocked.

## Outcomes and recovery

Per-action evidence distinguishes NotAttempted/known-not-sent, accepted-unverified, verified observed effect, rejected and uncertain; future/unknown values remain unclassified. HTTP success is not proof of propagation or complete offboarding. Readback may be delayed: save a review-required result and allow explicit read-only reconciliation; never repeat the write. Session revocation is not reversible and can take time; record the actual stamp/response and limitation. Licence restoration may lack capacity or fail to restore data. Account re-enable and membership reversal each require a fresh independent plan; they are not promised rollback.

The user-visible checklist can cite a completed verified action but cannot mark the entire joiner/mover/leaver journey complete while manual preservation, Exchange, application/device or uncertain steps remain. Jobs retain immutable observations and exact source citations; no history rewriting. Local export/import of lifecycle records is historical/untrusted, never approval or resumable write authority. Bounded schema/digest/source checks and backup/transfer exclusions follow existing evidence rules.

## Native, tests and release limits

Native flow: choose user and journey → inspect authority/readiness and manual steps → choose one registered action → preview exact before/proposed/consequence/access → deliberate final approval → one send → observed result/recovery. Show source tenant/operator/mode, copyable exact IDs and why each action is disabled. Cancelling preparation leaves no write; disconnect/close waits for owned execution/evidence preservation. Keep collection/execution outside WPF. Experimental runtime gates remain visible until required independent acceptance; no unattended CLI writer.

Failing-first tests cover every route/body/scope, mandatory `$ref`, wrong/self/emergency/synced/dynamic/role-eligible/unknown target, missing/null/empty/duplicate/read-cap states, inherited licence retention, capacity/preservation refusal including add/update with newly disabled plans and licence-bearing group removal, exact before/approval invalidation, immutable inputs, timeout/cancel/crash around intent/send/readback, one-send/no retry, partial/unknown outcomes, cross-family unresolved blocking, read-only reconciliation and no imported authority. Windows/App/native three-size/keyboard/portable offline checks use synthetic sources and zero tenant calls. Source implementation, synthetic/native validation and actual Microsoft behaviour stay separately labelled. Named safety review, H1/accessibility and live action/consent remain separate gates.

Rollback removes/disables the additive registry/native entry while keeping original plans/runs readable and unresolved records blocking writes. No automatic remote undo or deletion of safety history.
