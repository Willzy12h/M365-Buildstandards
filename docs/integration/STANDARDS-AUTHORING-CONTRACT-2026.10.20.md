# Offline candidate standards authoring — INT-136

Decision-only contract for approved expansion I/recommendation9. Base main0fc5419911f784fadae14803283ac9a138edb046. It neither publishes a catalogue nor accepts a candidate for deployment. Dependent implementation waits for this decision's reviewed merge. Existing named safety reviews still apply where implementation changes execution, evidence or context admission.

## Reuse and boundary

Reuse `StandardsLoader`, `StandardCatalogue`, `PolicyImporter`/`DevicePolicyImporter`, `NamingConvention`, `PolicyInputValidator`, `WritePayloadGuard`, `PolicyCandidateSafety`, `ReleaseLineage` and the existing standard-definition exporters. `AutomationViewModel.Import` already accepts a supported single-policy import with explicit replacements; do not rebuild or silently change that workflow. `StandardViewModel` already exports the definition and engineer document; extend its native offline authoring journey rather than replace the page or the WPF shell.

New responsibility: a deterministic, independently versioned **candidate draft** with an exact verified baseline, explicitly selected local changes, unresolved-reference diagnostics and separate configuration/assignment comparison. It is not another deployed standard schema, evidence snapshot, completion record, policy ownership claim or executable plan. No Graph calls, sign-in, new scopes, scripts, tenant writes, new framework or database. Published standards/manifests/lineages and original imported files are never edited.

## Identity and bounded document

Use an additive `standard-candidate-draft` schemaVersion1 JSON envelope. Required fields: kind/version; baseline release, full original-file SHA-256 and catalogue schema version; candidate title; ordered selected changes; source-import references with original byte SHA-256 and registered control/type; unresolved input records; configuration comparison; separately labelled assignment observations; canonical content digest. File paths, client profiles, tenant evidence, tokens and timestamps are not identity inputs. An explicit saved-at UTC timestamp may be envelope metadata, outside deterministic candidate content, and is not proof of authorship.

Read at most8MiB with maximum JSON depth48; reject duplicate property names case-insensitively, unknown fields, null required collections, duplicate control/path edits, unsupported versions and invalid digests. Bound100controls,1000changes,100source imports and200unresolved references. Bounds are refusals with a clear error, never clipped-success output. Save/export uses the existing safe local output conventions, unique filenames and verified readback; never overwrite a published source or silently replace an existing draft. Import does not install or select a catalogue.

Load the baseline through the verified standards manifest. Release text alone is insufficient: require its exact file digest and schema. Missing, changed or unavailable baseline blocks validation/export; never bind to the newest same-name catalogue. Changing the active standard/context invalidates the projected comparison and validation ticket. Previously saved drafts retain their original baseline and remain recoverable as local files. History remains readable; no automatic migration/rebase.

## Editable scope and conflicts

The first editor supports existing registered controls, existing parameter defaults and supported recipe payload/settings fields. No new collection/API/scope/action, control-ID rename/deletion, executable prerequisite, licence rule, evidence mapping or capability flag may be authored by this surface. A new unsupported setting/shape needs a separately reviewed adapter, not raw unvalidated JSON execution.

Represent selected edits by exact control ID and RFC6901 JSON-pointer path with expected original value and proposed value. Paths are parsed as data, never executable expressions. Whole arrays are compared/edited atomically unless the existing supported importer explicitly identifies entries; array order is preserved. Before application, verify the expected value against the pinned baseline. Refuse duplicate, ancestor/descendant or conflicting overlays instead of last-write-wins; case differences cannot silently create a duplicate parameter/control. Do not mutate caller-owned baseline or draft objects.

Reuse the current importers for their supported policy types and shape checks, but a reusable candidate must not silently adopt the importer's tenant-specific replacement IDs. Present each foreign reference as unresolved with its source/control/path and require an explicit existing typed parameter mapping or supported baseline literal. A GUID already present as a documented recipe/type identifier is not automatically a tenant object; preserve known unchanged baseline literals. Unknown changed GUIDs or tenant-specific IDs remain unresolved, never replaced by a guessed GUID/name, arbitrary template expression or blank. New parameter declarations and new expression syntax are outside this first editor. Imports must not copy foreign assignments, object IDs, service metadata, role scope tags or embedded secrets into candidate configuration.

Only validated expected/current template expressions are admitted. Existing naming, parameter typing/range/required checks and recipe validation still apply. Candidate CA payloads remain disabled, with their exact reviewed targeting/exclusions preserved; authoring never clears targets to pretend unassigned. Intune candidate payloads remain unassigned. Activation, assignment, retirement and live renaming are unavailable here. macOS remains default-off/blocked under the existing accepted standard, not enabled by draft editing.

## Comparison, validation and export

Show original and proposed configuration by control/path, including additions/removals permitted by the registered recipe, original/proposed types and unsupported/unresolved reasons. Separate assignment observations from configuration differences, explicitly identifying source claims and dropped foreign scope. An unavailable assignment read is Unknown, not an empty assignment list. Assignment observations cannot be applied through this editor. Display imported source digests/limitations; integrity is not authentication.

Validate a deep-cloned proposed catalogue through existing validators/guards after every selected change. Only complete, conflict-free, resolved supported candidates may export a standalone catalogue JSON with Candidate status and deterministic content-derived candidate release identity. Clear loader-only IntegrityDigest/SourceFileName; do not give candidate bytes the baseline's verified digest or publication metadata. Candidate exports include their draft/provenance/diff as separate local outputs, and are never added to `standards/manifest.json`, lineage manifests or release pins. Do not claim a verified release lineage for a local candidate: show exact baseline provenance and require the existing reviewed new-standard publication process for a released successor.

Draft saving with unresolved items is allowed and visibly labelled **Draft — cannot export a validated candidate**. Saving is not validation. Candidate export requires a fresh validation ticket bound to the exact baseline digest and canonical draft content; editing, source replacement or standard change invalidates it. Export recomputes/validates in the shared engine, rather than trusting an enabled WPF button. No automatic use of the candidate in the current tenant session or transfer of prior assessment/approval. Existing deliberate catalogue-loading and fresh assessment/deployment gates remain unchanged.

## Usable surfaces and evidence

Native workflow: open verified baseline → select existing control/default → edit supported value or inspect a policy import → resolve supported parameter inputs → review configuration and separate assignment observations → validate → save draft/export candidate and comparison. Friendly control names lead; exact IDs/paths/digests are copyable. Disabled actions state the failing condition and next step. Unsaved edits receive an explicit keep/save/discard choice before baseline replacement/close; no hidden auto-save into a shared source. Long comparison work stays off the dispatcher, is cancellable and rechecks context before admission.

Offline CLI uses the same draft parser/validator/comparison/export services, with deterministic JSON and readable HTML comparison. It neither signs in nor applies a draft. Existing standard export commands and historical importer behaviour are retained. No full web editor: the contained catalogue reader remains reference-only.

Meaningful failing-first tests cover exact baseline binding, old-catalogue byte identity, deterministic output, caller immutability, duplicate/case/overlapping edits, stale expected values, wrong object type/unknown shape, bounds/unknown fields, foreign references, unsupported/new expressions, separate unknown assignments, CA/Intune/macOS safety, invalidated validation tickets, interrupted/failed local writes and no implied publication/tenant authority. Native tests cover editing/selection/validation/export, context changes, unsaved navigation, three harness sizes, keyboard/accessibility names and actionable failure text. Portable CLI/package checks use synthetic drafts and originals; no tenant calls. Actual Windows/native evidence remains distinct from Linux cross-compilation. Named review, human accessibility/H1 and release acceptance remain separate.

Rollback disables/removes the additive editor registration while preserving saved draft files and original source/evidence. It performs no tenant reversal and no historical manifest rewrite. Publication, live use and any materially broader authoring surface require their existing separate approval.
