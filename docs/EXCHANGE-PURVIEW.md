# Exchange and Purview observations

In **Configuration > Exchange & Purview**, connect the client and select **Capture Exchange and Purview · read-only**. The toolkit uses the verified tenant and signed-in account, checks the installed module, starts a fresh owned Windows PowerShell process and runs its embedded read template. It verifies the observed Exchange and Purview tenant before reading each collection, reports progress and imports the resulting observations automatically. Stop cancels and terminates only the owned process; no partial file is imported after cancellation.

Windows PowerShell 5.1 and a preinstalled supported **ExchangeOnlineManagement 3.7.0 or later** are required for integrated capture. Install/maintain the module through your organisation's approved process; the toolkit neither installs it nor bypasses execution policy. WAM is the module's default. A separate PowerShell window may appear while Microsoft handles sign-in. Exchange/Purview have their own token audiences and read RBAC, so Graph sign-in alone does not establish access and Microsoft can require another prompt. Read-only RBAC and live module/service outcomes need engineer acceptance. See Microsoft's [Exchange connection documentation](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/connect-exchangeonline?view=exchange-ps) and [Purview connection documentation](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/connect-ippssession?view=exchange-ps), reviewed 1 October 2026.

No mail domain needs typing for integrated organisation-wide capture. The connected primary domain supplies the existing schema's reference domain. Select a discovered **accepted mail domain** for DKIM, DMARC and domain-specific rules. Accepted-domain failure leaves those checks unknown while organisation-wide observations can still be assessed. Selecting another domain clears prior DNS answers; **Check DKIM and DMARC DNS** reads both selector CNAMEs and the DMARC TXT record without tenant authentication. No tenant or DNS settings are changed.

Exchange/Purview observations are saved separately from Graph evidence. Collection, import, DNS and domain selection preserve the current Graph capture, live status, plan and evidence acknowledgement; they cannot satisfy its deployment checks. Assessment identifies the separate source/time. **Export Exchange/Purview observations** saves the separate evidence as JSON. A saved/imported file's provenance claims are not signed, even if originally collected by the tool.

**Offline import and manual export** remains available: enter the capture's domain, export/review the script and run it manually in a fresh process, or import an existing JSON file. Manual capture supports installed module 3.2.0 or later; WAM availability depends on module version. Offline observations cannot become Graph before-change evidence.

The importer accepts only the capture schema's projected configuration fields, within 2 MiB. Unknown or duplicate fields, other tenants, non-delegated provenance, invalid timestamps and supplied DNS answers are refused. Source claims are **not independently authenticated**. Missing properties, failed reads and old observations remain unknown. A matching setting still requires manual verification of effective service behaviour, permissions and licensing.

The capture includes audit ingestion and retention policies, transport rules, both preset policy components, outbound forwarding policies, SMTP AUTH, external tags, mailbox audit configuration and DKIM. It excludes mailbox contents, audit events, credentials and connection objects. Purview retention collection is optional; a failed or omitted read does not establish absence. Default audit retention and entitlement must be checked for affected users; no retention or DLP policy is changed.

DKIM displays the **actual returned** selector targets. Both fresh DNS answers must match those targets before readiness can be reported. This is one resolver's view and does not establish successful message signing. DMARC reports presence and basic policy syntax; it is not a full RFC validator and does not change DNS. Check alignment, reporting destinations and actual mail manually.

The supported module has internal retries. Consequently, this release does not execute Exchange writes in the toolkit; see the fallback decision in [the recorded API investigation](https://github.com/Willzy12h/M365-Buildstandards/blob/c987c05d5b95005451becaea4f097782425978ab/docs/integration/API-INVESTIGATION-2026.09.12.md). The own-domain SPF spam-bypass rule also has an unverified header-trust/alignment boundary and must not be labelled spoof-safe.

## Selected manual proposals

After importing complete, fresh observations, choose one control under **Review a manual change proposal**, type the selected client's full tenant ID, and export. The saved capture must pass its integrity check and match the reviewed in-memory evidence and entered domain. The resulting `.ps1` is a review document: invoking it throws immediately and every instruction/command is a line comment. It contains the selected control's before observations, portal steps, PowerShell reference and after checks. It grants no deployment authorisation and must be kept with confidential client evidence, outside source control.

Review individual commands under the client's change process. Save fresh before evidence and durable intent before each manual request, verify the connected tenant, repeat typed confirmation, preserve unrelated settings and read back the exact affected object. After an uncertain result, stop and reconcile; do not repeat the request. The module's internal retries remain outside the toolkit's control.

The bypass proposal creates only a disabled audit candidate, with exact From-domain and SPF-pass predicates and SCL -1; it includes no activation command. Existing rule names are conflicts, not ownership. DKIM enabling commands are omitted until both fresh CNAME observations match the actual captured targets; those commands also recheck both records manually. An absent DKIM configuration receives only disabled creation and recapture instructions. Retention and DMARC remain report-only. These same catalogue instructions feed the manual implementation guide.

## Source contracts and verification limits

- [Exchange connection information](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/get-connectioninformation?view=exchange-ps): `TenantID`, `State` and `IsEopSession` are checked before each scripted read. Command import allow-lists do not grant or constrain RBAC on their own.
- [Exchange Online module](https://learn.microsoft.com/en-us/powershell/exchange/exchange-online-powershell-v2): use a supported module/runtime pairing; no administrator requirement, installation or execution-policy change is introduced by the toolkit.
- [DKIM configuration](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dkim-configure): use the service's returned CNAME targets, never construct them from an assumed format.
- [DMARC syntax and manual rollout](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-dmarc-configure): review policy, percentage, alignment and reporting before enforcement.
- [Resolve-DnsName](https://learn.microsoft.com/en-us/powershell/module/dnsclient/resolve-dnsname?view=windowsserver2025-ps) and [Windows DNS error codes](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--9000-11999-): the fixed Windows adapter uses DNS-only CNAME/TXT questions, excludes the hosts file, and distinguishes explicit absence from errors.

Implementation and tests use synthetic fixtures only. Actual Exchange/Purview responses, module/runtime compatibility, DNS resolver behaviour, service effects and licences remain **unverified**. The interface harness never presses the DNS action and never executes an exported script.

## Confirmed account during integrated capture — PR #59

Integrated capture uses the verified Graph session's sign-in name as a hint, then independently checks the account returned by Exchange/Purview alongside its tenant and resource. It does not treat the hint as proof that Microsoft selected that account. An empty/display-only name refuses before temporary files or a process are created; reconnect and verify the account. An unknown/different account or ambiguous tenant/resource refuses the initial read. The same identity check runs before every collection, so an account/session change makes that collection unknown/error rather than an empty success. Prior observations retain their original read status; there is no interactive retry or silent account switch mid-capture.

This does not share Graph tokens/caches with PowerShell or promise zero Microsoft prompts. Separate Exchange/Purview consent, CA/MFA and read-only RBAC still apply; the supported installed module is required and is not installed by the toolkit. If module, runtime or application control blocks execution, use the organisation's approved provisioning/security-owner route; no policy change or alternate host bypass is provided.

A manually exported script without a supplied sign-in name retains its historical tenant-only boundary. Supply `-UserPrincipalName` to pin that manual run too; absent account metadata cannot establish account proof in a historical schema-1 export. This change does not add actor fields, alter historical evidence or confer deployment authority.

## Registered mailbox setting reports (INT-121)

The existing read-only Run surface additionally registers protocol, forwarding and hold-setting reports. These remain experimental/live-unverified, require current exact-context opt-in/review and use the same owned process, protected connection admission, cancellation, result validation and original-output recovery. They never satisfy deployment before-evidence or licence eligibility, and perform no Exchange changes. The other29 Copy/Save entries keep their original manifests and body pins.

Protocol inventory starts with the exact ExchangeGuid and Entra object ID returned by the mailbox inventory. Each protocol query uses Microsoft’s documented `Get-CASMailbox -Identity <ExchangeGuid>` path and accepts settings only when exactly one result repeats that exact Entra ID. No name/address join or fallback is made; a mailbox without a joinable ID remains explicitly partial/unknown. Returned null SMTP AUTH override means Inherit; an absent or malformed override means Unknown. The derived organisation/mailbox configuration is not proof of successful authentication: CA, authentication policies and other Microsoft controls remain relevant.

Forwarding preserves the returned address and SMTP target separately. Collected null means explicitly unset; unread values remain unknown. Hold flags and up to100 exact InPlaceHolds identifiers are observations, not a legal/compliance conclusion. A returned empty collection remains empty; missing/null/malformed/excess identifiers are unknown, never an empty success. Collection is capped before excluding unidentified mailboxes; truncation/missing identities remain Partial. Duplicate identities refuse evidence.

No Graph permission is added. Recipient read access is needed; protocol reporting also reads the organisation transport configuration. Existing `View-Only Recipients` / `View-Only Organization Management` requirements are documented suggestions, not live-verified RBAC proof. Use existing authorised roles; an unavailable cmdlet or property remains an explicit incomplete read. The toolkit installs no modules, grants no consent and attempts no fallback host or policy bypass.

Primary references inspected15October2026: [mailbox property sets](https://learn.microsoft.com/en-us/powershell/exchange/cmdlet-property-sets?view=exchange-ps), [mailbox protocol identity options](https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/get-casmailbox?view=exchange-ps), [SMTP AUTH configuration and inheritance](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/authenticated-client-smtp-submission). Property/module shapes and required roles still need separate human/live acceptance.

The hold report requests documented LitigationHoldEnabled, RetentionHoldEnabled, ComplianceTagHoldApplied, DelayHoldApplied and InPlaceHolds properties. It does not assess DelayReleaseHoldApplied or tenant-wide policy effects. This avoids requesting a property absent from the chosen cmdlet’s documented property sets.

## Offline registered Exchange report export

Use `buildstandard exchange-report-evidence --input <report.json> --tenant <expected-tenant-guid> --format html --root <local-workspace>` to inspect a supplied registered Exchange report without signing in. Formats are `html`, `csv`, `xlsx` and `json`. This command accepts only the separate `exchangeReportEvidence` kind; the Graph `report-evidence` command remains separate. It cannot capture, run scripts, save tenant evidence or change a tenant.

HTML, CSV and Excel include the recorded section/read states and an explicit supplied-file notice. JSON produces a ZIP containing the exact original `report.json` (including BOM/whitespace) and a provenance README; extract the original JSON for later offline inspection. Each export identifies the original file SHA-256. A digest detects modification, not authenticity of source, tenant/account or live-mode claims. No imported record becomes current deployment before-evidence.

The new report2 inbox-rule reader separates selected-target outcomes from rule observations, preserves opaque rule identities and labels local observation keys separately from Microsoft IDs. Reported false, zero and empty lists remain distinct from null, missing, failed and unsupported values. Unresolved reference labels are not directory joins. The typed reader and offline export alone do not enable an executable inbox-rule script; use only the runnable entries actually present in the verified package. Hidden-rule scope and source/RBAC limits remain explicit; an empty list is not an incident verdict.

Local inbox-rule review cues highlight returned forwarding recipients, `DeleteMessage=true` and `MarkAsRead=true`, while retaining unknowns and unresolved references. Recorded disabled rules remain visible: configuration does not prove effective behaviour. “No selected cues reported” is not a safety verdict, a hidden-rule check or proof that no other rules exist. These derived display columns do not change the stored observations or authorise remediation.
